# bd CLI — что и как используем

> Скилл `prd-to-beads` **оборачивает** `bd` CLI, не переизобретает его. Здесь —
> минимально необходимый набор команд и флагов для Mode 2 (создание beads
> из tasks.md). Полную документацию см. в `bd <command> --help`.

## Предполётная проверка

```bash
bd --version          # есть ли beads
bd list --limit 1     # инициализирован ли репо (если нет — bd init)
```

Если `bd init` не сделан в проекте — отказывай в коммите и проси юзера
инициализировать: `cd <repo> && bd init`. Не запускай `bd init` сам без
подтверждения (это создаёт `.beads/` в репо).

## Создание задачи (основная команда)

```bash
BD_ID=$(bd create "<title>" \
  --body-file - \
  --priority <0..4> \
  --labels "<csv-labels>" \
  --external-ref "prd:<slug>#T-N" \
  --silent <<'EOF'
<полное тело задачи markdown>
EOF
)
echo "$BD_ID"   # например: bd-42
```

**Флаги, которые скилл использует обязательно:**

| Флаг | Зачем |
|------|-------|
| `--body-file -` | многострочный markdown через stdin (heredoc) — не нужно экранировать кавычки/бэктики |
| `--silent` | вывод только ID — нужно для парсинга и сохранения в frontmatter `committed_ids` |
| `--external-ref "prd:<slug>#T-N"` | трассировка обратно к задаче в tasks.md |
| `--priority` | из поля «Приоритет» задачи (P0–P3 → 0..3) |
| `--labels "feature:<slug>,vertical-slice"` | для последующей фильтрации `bd list -l feature:<slug>` |

**Опционально, если уместно:**

| Флаг | Когда |
|------|-------|
| `--parent <epic-id>` | если для фичи был создан отдельный epic-issue |
| `--acceptance "<short>"` | короткая выжимка из Gherkin (одна строка) |

**Не использовать без явного запроса юзера:**

- `--assignee` — кто будет делать, скилл не знает
- `--due`, `--defer` — даты, скилл не знает
- `--estimate` — оценка трудоёмкости, не угадываем

## Зависимости между задачами

Связи скилл не ставит по своему усмотрению: их предлагает Mode 1 и
подтверждает юзер, после чего они лежат в поле
`**Зависит от:** T-M — <почему>` каждой задачи tasks.md. Mode 2 создаёт
ровно их — после того как созданы все issues и известны все bd-id:

```bash
bd dep add <bd-id-зависимой> <bd-id-блокера> --sandbox
```

Порядок аргументов — сначала зависимая задача, потом блокер. Тип связи по
умолчанию `blocks`, флаг `--type` не нужен.

**Идемпотентность связей.** Повторный вызов с той же парой дубля не
создаёт: команда печатает то же `✓ Added dependency` и выходит с кодом 0,
а `bd show <id>` показывает одну связь (проверено на bd 1.2.2). Поэтому
при доливке новых задач в уже закоммиченный tasks.md безопасно прогнать
связи для всех задач подряд — существующие просто подтвердятся, новые
встанут.

**Цикл.** Если связи образуют цикл, `bd dep add` отказывает:
`Error: adding dependency would create a cycle`, код выхода 1. К этому
моменту issues уже созданы, поэтому граф проверяется раньше — в Mode 1,
на шаге подтверждения связей.

Проверить результат: `bd dep list <id>` — блокеры одной задачи,
`bd ready` — задачи без незакрытых блокеров.

## Совместимость и синхронизация

Перед записью прочитайте `bd prime`, `bd create --help` и `bd dep add --help` установленной версии.
Примеры оболочки выше рассчитаны на POSIX. В PowerShell передавайте тело через временный UTF-8 файл и `--body-file <path>`.
Флаг `--sandbox` используйте только если он поддерживается установленной версией и нужен её режиму работы.
Пакет не настраивает remote. Не выполняйте `bd dolt push` без поручения пользователя.
Создание локальных задач не требует их публикации.

## Идемпотентность

Mode 2 запускается ровно один раз для tasks.md. Чтобы избежать
двойного коммита:

1. **До** первого `bd create`: проверь `frontmatter.status == "reviewed"`.
   Любое другое значение → отказ.
2. **После** успешного коммита: перепиши frontmatter:
   - `status: committed`
   - `committed_ids: { "T-1": "bd-42", "T-2": "bd-43", ... }`
   - `committed_at: ГГГГ-ММ-ДД`
3. Связи (`bd dep add`) идемпотентны сами по себе, отдельной защиты не
   требуют: прогоняй их для всех задач файла после создания issues.
4. Если в процессе любая `bd create` упала — **прервать** дальнейшие, не
   откатывать уже созданные (это требовало бы `bd delete`, что чревато
   потерей данных), сообщить юзеру какие T-N успели создаться (с их
   bd-id) и какая упала. Юзер вручную решает дальше.

## Защита от двойного запуска

Если `status == "committed"` — отказывай в коммите с сообщением:

> Этот tasks.md уже закоммичен (см. `committed_ids` во frontmatter).
> Если нужно создать дополнительные задачи — отредактируй tasks.md,
> добавь новые T-N, поменяй `status` обратно на `reviewed` и попроси
> залить только новые. (Уже существующие T-N с известным bd-id
> пропускаются при создании, но их id нужны для связей: `bd dep add`
> прогоняется по всем задачам файла — дублей это не создаёт.)

## Dry-run для предпросмотра

Перед фактическим коммитом полезно показать юзеру итоговый набор
команд (без выполнения):

```bash
bd create "<title>" --body-file - --dry-run <<'EOF'
...
EOF
```

`--dry-run` показывает что *было бы* создано, без записи в БД. Это
дешёвый sanity check для самой первой задачи перед массовым коммитом.
