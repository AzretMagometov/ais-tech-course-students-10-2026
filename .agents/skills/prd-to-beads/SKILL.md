---
name: prd-to-beads
description: >
  Разбивает PRD-документ на вертикальные задачи (UI + Domain + Data) в два
  этапа: сначала генерирует ревьюабельный markdown-файл
  docs/features/{slug}/tasks.md (Mode 1), потом — после ручного review и
  выставления status: reviewed — создаёт beads-issues через bd CLI (Mode 2).
  Задача — вертикальный срез по User Story: ссылки на FR, затрагиваемые
  классы/функции (из §6.5 PRD), Gherkin happy path, edge cases,
  наблюдаемый результат и подтверждённые юзером блокирующие связи.
  Подготовительный рефакторинг выносится в первые задачи.
  Реализация задач предполагается через /senior-developer (TDD).
  Триггеры Mode 1 (draft): «разбей PRD на задачи», «декомпозируй PRD»,
  «сгенерируй задачи по спеке», «PRD to tasks», «создай задачи по фиче {slug}»,
  «/prd-to-beads».
  Триггеры Mode 2 (commit): «залей задачи в beads», «создай beads из
  {slug}», «commit tasks», «залить в беды», «закоммить tasks.md».
  Does NOT write code, does NOT execute beads tasks, does NOT edit the PRD,
  does NOT invent classes/functions absent from PRD §6.5.

## Использование в учебной копии

Работайте в выбранном проекте участника. Для задачи дубликатов это `exercises/02-duplicate-finder/work/`.
Не изменяйте материалы курса ради реализации задания. Относительные ссылки на справочники разрешайте от папки скилла.
Инструкции проекта и поручение пользователя имеют приоритет. Подключение скилла не разрешает коммит или публикацию.


# PRD → Beads Decomposer

Скилл состоит из **двух режимов**. Сначала всегда определи, какой
запрашивает пользователь.

## Определение режима

| Сигнал в запросе | Режим |
|------------------|-------|
| «разбей PRD», «декомпозируй», «сгенерируй задачи», «PRD to tasks» | **Mode 1: draft** |
| «залей в beads», «закоммить», «commit tasks», «создай beads из …» | **Mode 2: commit** |
| Не ясно — спроси одной фразой: «Сделать draft tasks.md или закоммитить уже отревьюенный?» | — |

Если в проекте нет `.beads/` — Mode 2 откажет (см. `references/beads-cli.md`).
Mode 1 работает в любом проекте.

## Mode 1: Draft (PRD → tasks.md)

### Шаги

1. **Найти PRD.** Раскладка папки фичи и корень фич — в
   `../_shared/feature-docs.md`. PRD лежит в
   `<root>/<slug>/prd.md`, корень по умолчанию — `docs/features/`. Если
   проект задаёт свой корень в `CLAUDE.md`, ищи папку `<slug>/`
   рекурсивно (Glob) под этим корнем.
   - Если дан путь к папке фичи или к `prd.md` → бери его.
   - Если дан slug → найди `<root>/<slug>/prd.md`.
   - Если ничего не указано → выведи найденные `<root>/*/prd.md` и спроси.
   - Если файла нет → отказ + ссылка на `/create-prd`.
   - **Запомни папку, где нашёл PRD** (`<feature-dir>`). `tasks.md` пиши
     в неё же, проект заново не определяй.

2. **Валидация PRD.** Прочитай файл. Проверки:
   - Строка `**Статус:**` в шапке PRD — `Approved` или `Review`; иначе предупреди
     (но не блокируй, юзер может работать с draft PRD на свой риск).
   - Секция **§6.5 «Затрагиваемые классы и функции»** — присутствует и
     не пуста. Если её нет / пустая → **отказ**:
     > PRD не содержит §6.5 (Затрагиваемые классы и функции). Без неё
     > я не могу собрать вертикальные задачи. Дополни PRD через
     > /create-prd или вручную, потом возвращайся.
   - Секция **§4 User Stories** — содержит хотя бы один US-N. Иначе → отказ.
   - Секции §5 (FR), §6.1 (Архитектура) — желательны; их отсутствие
     понижает качество, но не блокирует.

3. **Скан репозитория.** Проверь правдоподобность путей из §6.5:
   - Для `[EDIT]` — файл существует на диске? Если нет → пометка `[?]`.
   - Для `[NEW]` — родительский каталог существует и соответствует
     соглашениям проекта (наличие соседних файлов того же типа)?
   - При расхождениях — задай 1–2 уточняющих вопроса юзеру **до**
     генерации tasks.md, не после.

4. **Маппинг US → задачи.** Для каждого US-N:
   - Сматчить FR-* из §5, упоминающие роль/действие/сущность из US.
   - Сматчить классы/функции из §6.5, реализующие эти FR. Разнести по
     слоям (UI / Domain / Data) на основе того, в какую секцию-слой §6.5
     они попали в PRD.
   - Сгенерировать **Gherkin happy path** (3–6 шагов) на основе главного
     флоу US и связанных FR.
   - Сгенерировать **edge cases** (3–6 строк) из: §6.2 ошибок API, §9
     рисков, очевидных невалидных входов, граничных значений.
   - Сформулировать **«Что покажем, когда готово»** — одну строку про
     наблюдаемый результат: экран, команда, запрос или отчёт, который
     после задачи работает, а до неё не работал. Проверка формулировки:
     на текущем коммите это утверждение должно быть ложным. Если оно уже
     верно или описывает слой («репозиторий написан», «эндпоинт есть»), а
     не поведение — перед тобой горизонтальный срез, задачу надо собрать
     заново.

5. **Подготовительный рефакторинг — первыми задачами.** Если задачам нужна
   перестройка уже существующего кода, она не размазывается по задачам
   фичи, а выносится в отдельные задачи в начало списка.

   Признаки — по тем же полям §6.5, без новых секций в PRD:
   - строка `[EDIT]` попала в списки двух и более задач: общий код правят
     несколько срезов, значит правим его один раз заранее;
   - описание строки `[EDIT]` структурное — «вынести», «переименовать»,
     «разделить», «заменить», «перевести на», «обобщить»;
   - скан репо (шаг 3) показал, что `[NEW]`-файл не встаёт в текущую
     структуру без переноса соседей.

   Такие строки собираются в задачи в начале списка; каждая задача фичи,
   которая их ждёт, получает на них блокирующую связь (шаг 7).

   **Широкая перестройка — схема expand–contract.** Широкая перестройка —
   это одно механическое изменение (переименовать колонку, сменить тип
   общего символа), которое задевает сразу сотни мест вызова: вертикальным
   срезом её не сделать, любая половина оставляет проект красным.
   Раскладываем на три шага. Сначала расширение: новая форма добавляется
   рядом со старой, старая продолжает работать, ничего не ломается. Потом
   перевод потребителей — пакетами по зоне охвата (модуль, каталог,
   пакет), каждый пакет отдельной задачей, заблокированной
   задачей-расширением; тесты зелёные на каждом шаге, потому что старая
   форма ещё на месте. В конце сжатие: старая форма удаляется отдельной
   задачей, заблокированной всеми задачами перевода. Если и отдельный
   пакет зелёным не остаётся — последовательность та же, но все задачи
   перевода блокируют финальную задачу «собрать и проверить», и зелёное
   обещано только в ней.

6. **Размер задачи — одна сессия сабагента.** Задачу будет исполнять
   `/senior-developer` в отдельной сессии, которая PRD не видела: всё
   нужное должно уместиться в один контекст вместе с кодом и тестами.

   Проверяемый признак — два счётчика из самого PRD (дефолты, юзер вправе
   поднять или опустить их при ревью):
   - **не больше 3 FR** из §5 в поле «Связанные FR»;
   - **не больше 8 строк §6.5** суммарно по всем слоям задачи.

   Превышен один счётчик → перечитай задачу, почти всегда внутри два
   сценария. Превышены оба → режь обязательно.

   Как резать:
   1. **По сценариям** — основной способ. У US несколько самостоятельных
      флоу (создать / отредактировать / удалить; ручной ввод / импорт) →
      каждый флоу отдельной задачей. Срез остаётся вертикальным, у каждой
      задачи свой «Что покажем».
   2. **По слоям** — только если сценарий неделим (одна форма, один
      запрос, но очень широкий). Тогда получается цепочка
      Data → Domain → UI с блокирующими связями, и настоящий «Что покажем»
      есть только у верхней задачи; у нижних это «прогнать такой-то тест
      или миграцию и увидеть такой-то результат». Разрез по слоям —
      исключение, назови его юзеру отдельной строкой в предпросмотре.

   Чего не делаем: «половину задачи сейчас, половину потом». Задача без
   наблюдаемого результата — не задача.

7. **Блокирующие связи — предложить и подтвердить.** Связи выводит скилл,
   принимает юзер. Без подтверждения связь не считается принятой и в
   tasks.md не попадает.

   T-B блокируется T-A, когда:
   - в списке §6.5 задачи T-B есть `[EDIT]` того файла или символа,
     который T-A заводит как `[NEW]`;
   - «Дано» в Gherkin T-B опирается на результат T-A — экран, право,
     таблицу, данные, которых до T-A нет;
   - T-A — подготовительный рефакторинг (шаг 5), затрагивающий файлы T-B.

   Связью НЕ считается: задачи трогают один файл в разных местах; задачи
   лежат в одном слое; «логично сначала бэкенд». Пересечение по файлам без
   новой сущности — риск конфликта при слиянии: скажи о нём в
   предпросмотре, но блокирующей связи он не даёт.

   Покажи юзеру **одним** сообщением нумерованный список задач:

   ```
   T-1. Вынести сборку фильтров в FilterService
        связей нет · размер: 2 FR, 5 строк §6.5
        покажем: отчёты строятся как раньше, фильтры собирает FilterService
   T-2. Журнал выгрузок export_log
        связей нет · размер: 1 FR, 3 строки §6.5
        покажем: после тестового экспорта в export_log появляется запись
   T-3. Страница «Экспорт» со скачиванием CSV
        ← T-1: страница берёт фильтры из FilterService
        ← T-2: экспорт пишет в таблицу export_log, её заводит T-2
        размер: 3 FR, 7 строк §6.5
        покажем: аналитик открывает «Экспорт», выбирает период, получает файл
   ```

   И спроси одним вопросом: «Связи верные — ничего лишнего, ничего не
   пропущено? Гранулярность нормальная или что-то слить / разрезать?»

   - Юзер подтвердил → связи идут в поле `**Зависит от:**` каждой задачи.
   - Юзер поправил → перестрой список и покажи ещё раз.
   - Юзер сказал «связей нет» или не ответил → у всех задач
     `**Зависит от:** нет`. Неподтверждённые связи не записываются никуда,
     даже комментарием.

   После подтверждения проверь граф на циклы: упорядочи задачи так, чтобы
   каждый блокер стоял выше своей зависимой. Не получилось — это цикл,
   покажи его юзеру и попроси убрать одну связь. `bd` цикл тоже ловит, но
   уже в Mode 2 и отказом, когда issues созданы.

8. **Сохранить tasks.md.**
   - Путь: `<feature-dir>/tasks.md`
   - Если файл уже существует → **предупреди и спроси**:
     перезаписать / создать `tasks.v2.md` / отменить.
   - Никогда не перезаписывай файл со `status: committed` без явного
     подтверждения юзера.

9. **Сообщить юзеру.** В чат:

   ```
   Draft tasks.md сохранён: <feature-dir>/tasks.md
   Задач: N (T-1..T-N), подтверждённых связей: M

   Что делать дальше:
   1. Открой файл, прочитай каждую задачу.
   2. Проверь классы/функции (особенно помеченные [?]).
   3. Проверь «Зависит от» и «Что покажем, когда готово» у каждой задачи.
   4. Поправь Gherkin / edge cases по своему вкусу.
   5. Когда готов — поменяй `status: draft` → `status: reviewed`
      и попроси «залей задачи в beads».
   ```

## Mode 2: Commit (tasks.md → beads-issues)

### Шаги

1. **Найти tasks.md.** По slug → `<root>/<slug>/tasks.md` (корень по
   умолчанию `docs/features/`, иначе рекурсивный Glob под корнем фич
   проекта). Если нет → отказ.

2. **Pre-flight.** См. `references/beads-cli.md`:
   - `bd --version` → доступен?
   - `.beads/` инициализирован в репо? Если нет → отказ + предложение
     `bd init` (но не запускать самому).

3. **Валидация tasks.md.**
   - `frontmatter.status == "reviewed"` → продолжай.
   - `status == "draft"` → отказ: «tasks.md ещё в draft. Отревьюй и поменяй
     status на reviewed, потом возвращайся.»
   - `status == "committed"` → отказ (см. идемпотентность ниже и
     `beads-cli.md`).
   - Любое другое значение → отказ с указанием проблемы.

4. **Парсинг задач.** Для каждой `## T-N. <title>` секции собери:
   - title (после `T-N.`)
   - тело задачи (всё до следующей `## T-`) — это пойдёт в `--body-file -`
   - приоритет из строки `**Приоритет:** P<n>`
   - подтверждённые блокеры из строки
     `**Зависит от:** T-M — <почему>`: всё до первого « — » — список id
     через запятую, остаток — причина, запятые в ней допустимы; значение
     `нет` → блокеров у задачи нет; строки нет совсем (файл сгенерирован
     до появления поля) → блокеров нет, связи не выдумывай

5. **Dry-run первой задачи.** Чтобы юзер увидел что получится:
   ```bash
   bd create "<title T-1>" --body-file - --dry-run <<'EOF'
   <body>
   EOF
   ```
   Покажи вывод и спроси «Создавать остальные?». Если юзер ОК — продолжай.

6. **Массовый коммит.** Для каждой T-N последовательно:
   - `BD_ID=$(bd create ... --silent <<'EOF' ... EOF)`
   - Запиши mapping `T-N → bd-ID`
   - Если упал — **прерви**, остальные не создавай. Сообщи юзеру какие
     успели, какая упала, почему.

7. **Зависимости.** После создания всех задач — по одной команде на каждый
   T-M из поля `**Зависит от:**`:
   - `bd dep add <bd-id-зависимой> <bd-id-блокера> --sandbox`
   - Повторный вызов с той же парой дубля не создаёт: команда отвечает
     успехом, связь в базе остаётся одна. Поэтому при доливке новых задач
     в уже закоммиченный tasks.md прогоняй связи для **всех** задач, а не
     только для новых, — блокеры на ранее созданные issues тоже встанут.
   - Связи, которых нет в поле «Зависит от», не создавай, даже если они
     кажутся очевидными: их не подтвердил юзер.

8. **Обновить frontmatter tasks.md.**
   - `status: committed`
   - `committed_at: ГГГГ-ММ-ДД`
   - `committed_ids: { "T-1": "bd-42", "T-2": "bd-43", ... }`

9. **Сообщить юзеру.**
   ```
   Создано beads-issues: N
   - T-1 → bd-42
   - T-2 → bd-43
   ...

   Зависимости: M связей
   Frontmatter tasks.md обновлён (status: committed).

   Дальше: запускай /senior-developer на ready-задачи (`bd ready --exclude-type decision,epic`).
   ```

## Что скилл НЕ делает

- **Не пишет код.** Это работа `/senior-developer` в отдельной сабагент-сессии.
- **Не выполняет beads-задачи** сам. Реализация — отдельный запуск `/senior-developer`.
- **Не редактирует PRD.** Если §6.5 пуста или User Stories отсутствуют —
  отказ + указание дополнить PRD через `/create-prd` или вручную.
- **Не выдумывает классы/функции,** которых нет в §6.5 PRD. Скан репо
  только верифицирует существующие, не достраивает недостающие.
- **Не принимает зависимости молча.** Блокирующие связи скилл предлагает
  и объясняет (Mode 1, шаг 7), а принимает их юзер. Mode 2 создаёт ровно
  то, что записано в поле `Зависит от`, и ничего сверх.
- **Не запускает `bd init`** без явного подтверждения (создаёт `.beads/`
  в репо — мутирующее действие).
- **Не запускает `bd delete`** для отката частично-успешного коммита
  (риск потери данных). При сбое — оставляет частично созданное и
  отчитывается юзеру.

## Тон и стиль

- Документы (tasks.md) на русском, код / Gherkin / SQL / JSON — английские
  ключевые слова, тело сценария на русском (как в шаблоне).
- При неясности (несостыковки в §6.5, неоднозначность путей) — задавай
  1–2 коротких вопроса **до** генерации, не после. Не угадывай молча.
- При отказах — короткое сообщение + конкретное действие, что юзеру
  сделать дальше. Не «попробуй ещё раз» без объяснения.
