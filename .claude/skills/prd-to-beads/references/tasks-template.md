# Шаблон tasks-документа

> Этот файл — спецификация формата `<root>/<slug>/tasks.md`, который
> скилл `prd-to-beads` генерирует в **Mode 1** и читает в **Mode 2**.
>
> Документ — единственный источник правды для последующего создания
> beads-issues. Что попало в tasks.md → попадёт в beads. Что не попало —
> не попадёт.

## Жизненный цикл frontmatter

```
draft        # сразу после генерации (Mode 1)
  ↓ (user ревьюит, правит, выставляет вручную)
reviewed     # признак, что user одобрил содержимое
  ↓ (Mode 2 создаёт beads и переписывает frontmatter)
committed    # необратимо: задачи уже в beads, дальнейшие правки
             # tasks.md не вызывают повторного коммита
```

Mode 2 **отказывает** в коммите если `status` не равен `reviewed`.
После коммита Mode 2 пишет `committed_ids` (mapping T-N → bd-id).

## Структура файла

````markdown
---
slug: <slug>
prd: <root>/<slug>/prd.md
status: draft   # draft | reviewed | committed
generated: ГГГГ-ММ-ДД
committed_ids: {}   # заполняется Mode 2: { "T-1": "bd-42", "T-2": "bd-43" }
committed_at:       # заполняется Mode 2: ГГГГ-ММ-ДД
---

# Задачи: [Название фичи из PRD]

> Документ собран скиллом `prd-to-beads` из [PRD](./prd.md).
> Задачи по User Stories — **вертикальные срезы** (UI + Domain + Data);
> перед ними идут подготовительные рефакторинги, если они нужны.
>
> **Как ревьюить:**
> 1. Прочитай каждую T-N. Проверь что описание классов/функций совпадает с
>    реальной структурой кода (или что новые файлы названы корректно по
>    конвенциям проекта).
> 2. Проверь поле «Зависит от»: связь настоящая, если без блокера задачу
>    физически не начать. «Логично сначала бэкенд» — не связь, убирай.
> 3. Проверь поле «Что покажем, когда готово»: это должно быть поведение,
>    которое сегодня не работает, а не название слоя. Нет ответа — задача
>    нарезана по слоям, а не вертикально.
> 4. Прикинь размер: задача должна уместиться в одну сессию сабагента
>    (ориентир — до 3 FR и до 8 строк §6.5).
> 5. Поправь Gherkin-сценарии и edge cases по своему вкусу.
> 6. Можешь удалить, разбить, объединить задачи — всё что в файле остаётся
>    после ревью, попадёт в beads as is. Если номера T-N сдвинулись —
>    поправь ссылки в полях «Зависит от», иначе Mode 2 не найдёт блокера.
> 7. Когда готов — поменяй `status: draft` на `status: reviewed` и попроси
>    «залить задачи в beads».
````

## Правила генерации (для Mode 1)

### Маппинг PRD → tasks.md

| Из PRD | В tasks.md |
|--------|------------|
| Каждая строка `US-N` из §4 | Минимум одна задача; номер T-N с номером US не совпадает, связь держит поле `User Story` |
| Строка `[EDIT]` из §6.5, нужная нескольким US, или со структурным описанием («вынести», «переименовать», «разделить») | Отдельная подготовительная задача в начале списка |
| FR-* из §5, упоминающие сущности из US | `Связанные FR` задачи |
| §6.5 классы/функции, относящиеся к US | `Затрагиваемые классы и функции`, разнесённые по слоям |
| Концепт §1.5 + §5 FR | Источник для Gherkin happy path и строки `Что покажем, когда готово` |
| §3 «Не в скоупе», пункты, которые касаются задачи | `Не делаем` задачи |
| §9 риски (если есть) | Источник для edge cases |
| §6.2 API ошибки 4xx | Источник для edge cases (валидация / права) |

**Нумерация.** `T-N` — порядок выполнения: подготовительные рефакторинги
первыми, затем задачи по User Stories. Номера сквозные; на них ссылается
поле `Зависит от` и `--external-ref prd:<slug>#T-N` в Mode 2. Если при
ревью задачи добавились или исчезли — перенумеруй и поправь `Зависит от`.

### Что генератор делает сам

1. **Связь US ↔ FR.** Если в FR упоминается роль/действие из US → связан с этим US.
   Один FR может относиться к нескольким US — дублируй ссылку.
2. **Связь US ↔ классы/функции из 6.5.** Если класс/функция реализует FR,
   связанный с US → попадает в задачу. Один класс может появиться в нескольких
   T-N (например, общий сервис).
3. **Gherkin happy path.** Один сценарий из главного флоу US (3–6 шагов).
4. **Edge cases.** 3–6 строк маркированным списком: невалидный ввод,
   отсутствие прав, пустые выборки, граничные значения, сетевые ошибки.
5. **Что покажем, когда готово.** Одна строка про наблюдаемый результат:
   экран, команда, запрос или отчёт, который после задачи работает, а до
   неё не работал. Проверка: на текущем коммите утверждение должно быть
   ложным. У подготовительного рефакторинга наблюдаемое другое — прежние
   тесты зелёные, новая форма стоит рядом со старой, потребители переведены
   или ещё нет (см. пример T-1 выше).
6. **Подготовительный рефакторинг — вперёд.** Перестройка существующего
   кода не размазывается по задачам фичи, а собирается в отдельные задачи
   в начале списка. Широкая перестройка раскладывается по схеме
   expand–contract: расширение → перевод потребителей пакетами → сжатие
   (SKILL.md → Mode 1 → шаг 5).
7. **Блокирующие связи — предложить и подтвердить.** Генератор выводит
   связи (общий `[NEW]`-символ, «Дано» опирается на чужой результат,
   подготовительный рефакторинг), показывает их юзеру одним списком с
   причиной на строку и ждёт подтверждения. Подтверждённые попадают в поле
   `Зависит от`; неподтверждённые не записываются вообще (SKILL.md →
   Mode 1 → шаг 7).
8. **Размер задачи.** Ориентир — одна сессия сабагента: до 3 FR и до
   8 строк §6.5 на задачу. Не помещается — режем по сценариям, в крайнем
   случае по слоям; «половина задачи» не режется (SKILL.md → Mode 1 →
   шаг 6).

### Что генератор делает с помощью скана репо

См. SKILL.md → Mode 1 → шаг 3 «Скан репозитория».
Скан проверяет, существуют ли пути из §6.5 PRD на диске, и для `[NEW]` —
правдоподобны ли они с учётом структуры проекта. При расхождениях
помечает `[?]` и/или задаёт уточняющие вопросы пользователю **до**
сохранения tasks.md.

### Что генератор НЕ делает

- Не выдумывает классы / функции, которых нет в §6.5 PRD. Если §6.5 пуста
  или в ней нет нужных слоёв — отказывает и просит дополнить PRD.
- Не записывает блокирующие связи, которых юзер не подтвердил. Нет
  подтверждения → у всех задач `Зависит от: нет`.
- Не пишет код тестов (только Gherkin / описание). Тесты пишет
  `/senior-developer` в TDD-цикле уже на этапе исполнения beads-issue.
- Не создаёт beads сам. Это делает **только Mode 2** после `status: reviewed`.
