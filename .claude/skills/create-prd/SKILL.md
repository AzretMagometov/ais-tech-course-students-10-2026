## Использование в учебной копии

Работайте в выбранном проекте участника. Для задачи дубликатов это `exercises/02-duplicate-finder/work/`.
Не изменяйте материалы курса ради реализации задания. Относительные ссылки на справочники разрешайте от папки скилла.
Инструкции проекта и поручение пользователя имеют приоритет. Подключение скилла не разрешает коммит или публикацию.


# Create PRD Skill

Ты — генератор PRD-документов. Собери структурированный PRD из согласованного
поведения. Проведи пользователя через существенные технические развилки:
предложи варианты по фактам проекта, объясни последствия, зафиксируй выбор.
Мелкие обратимые детали решай сам. Не отправляй архитектуру обратно в
feature-discovery.

У скилла два входа:

| Вход | Когда | Источники |
|------|-------|-----------|
| **Карта wayfinder** | `/create-prd <map-id>`, «собери PRD по карте»; пользователь дал id эпика beads | тело карты, закрытые вопросы карты с комментариями, файлы findings, `CONTEXT.md`, `decisions.md`, репозиторий |
| **notes и tech.md** | `/create-prd <slug>`, путь к папке фичи или к `notes.md` | `notes.md` и `tech.md` скилла `feature-discovery`, репозиторий |

Id карты beads выглядит как `<prefix>-<hash>`, например `rag-quote-8ie`, и
`bd show <id>` его находит. Ничего не указано → выведи найденные
`<root>/*/notes.md` и, только при настроенном Beads, закрытые карты
(`bd list -t epic -l wayfinder:map --status closed --flat`), спроси, какой вход генерить (или возьми
единственный).

История разговора источником не является: скилл может запускаться в новой
сессии. Исключение — явные ответы пользователя на тех-интервью этого запуска.

Раскладка папки фичи, корень фич и правило slug — в
`../_shared/feature-docs.md`.

## Вход по карте wayfinder

Карта лежит в beads. Операции с ней — в
`../_shared/beads-tracker.md`, раздел «Wayfinding operations».
Карта — epic с меткой `wayfinder:map`. Её тело — description эпика. Вопросы —
дочерние issue типа `decision`. Скилл карту только читает, в beads не пишет.
Кроме PRD и блока SPEC он пишет только ADR тех-интервью в `decisions.md`.

### К1. Загрузка

1. `bd show <map-id>` — тип, метки, CHILDREN. Команда упала (нет базы beads,
   нет такого id) → скажи пользователю и остановись.
2. Тело карты дословно:
   ```bash
   bd show <map-id> --json | python3 -c 'import json,sys; sys.stdout.write(json.load(sys.stdin)[0]["description"])'
   ```
   id, пути и суть решений бери из этого вывода. `bd show` без `--json`
   переносит длинные строки и может разорвать id или путь на дефисе.

### К2. Проверки входа

По порядку, первая непройденная останавливает скилл:

1. Тип `epic` и метка `wayfinder:map`. Иначе: «<map-id> — не карта
   wayfinder».
2. Открытых вопросов нет: `bd list --parent <map-id> --flat` печатает пустой
   вывод. Без `--status` команда скрывает только закрытые. Есть строки →
   откажи:
   > Карта не закрыта, открытые вопросы: <название (id)>, …
   > Вернись в /wayfinder, реши их и запускай снова.
3. Раздел `## Концепт` есть, в нём четыре подраздела, и каждый заполнен: не
   пуст, не HTML-комментарий, не текст шаблона в `<...>`:
   `### Что это`, `### Для кого и какой опыт`, `### Главный принцип`,
   `### Чем это **не** является`. Иначе откажи:
   > Концепт карты не записан. Запусти /wayfinder <map-id>: сессия
   > сформулирует концепт с тобой и запишет его в карту.

Концепт записывает сессия `/wayfinder`, которая закрывает карту, и только
после подтверждения пользователя. Заполненный раздел и есть подтверждение.

**Не фича.** Destination описывает решение, миграцию или исследование, а не
новую возможность продукта → скажи: «Цель карты — <…>. Это не фича: PRD ей
не нужен» — и остановись.

### К3. Папка фичи

- В `## Notes` есть строка `Папка: <root>/<slug>/` → папка фичи
  (`<feature-dir>`) — она.
- Строки нет (карта старше этого правила) → `<root>/<slug>/`. Корень — по
  `feature-docs.md`. Slug — английский kebab-case по названию карты и
  Destination. Назови выбранный slug в выводе.
- `<feature-dir>/prd.md` уже есть → откажи: «PRD уже собран:
  <путь>. Удали или переименуй его, если нужна новая сборка». Не
  перезаписывай.

### К4. Чтение источников

1. **Тело карты** — все разделы. Destination, Notes (включая список
   ограничений, принятых при постановке), Decisions so far, Out of scope,
   Not yet specified, Концепт.
2. **Каждый закрытый вопрос** из CHILDREN:
   - `bd show <id>` — вопрос и причина закрытия. Причина закрытия бывает
     частью решения: выбранный вариант, номер ADR.
   - `bd comments <id> --json`, поле `text` — **все** комментарии, не только
     последний. Решение бывает разнесено по нескольким комментариям.
     Комментарии идут по времени. Более поздний уточняет или отменяет более
     ранний: бери итог.
   - Строка вопроса в Out of scope → вопрос вынесен за скоуп, решением не
     считается.
3. **Строки Decisions so far без вопроса** (решение пользователя, ADR) —
   источник наравне с вопросами. ADR из такой строки прочитай в
   `decisions.md`.
4. **Файлы findings** исследовательских вопросов. Комментарий называет путь:
   `Findings: <путь>`. Прочитай файл в рабочем дереве. Комментарий называет
   ветку (`branch <ветка>, file <путь>`) → `git show <ветка>:<путь>`.
   Файла нет нигде → путь идёт в §2 «Материалы» с пометкой «файл не
   найден».
5. **Прототипы** — ветка и путь из комментария идут в §2 «Материалы».
   Прототип не читай: решение по нему записано в комментарии.
6. **`decisions.md`** в корне проекта — ADR, на которые ссылаются тело карты
   и комментарии. «Alternatives Considered» и «Consequences» этих ADR —
   источник §8 и §9.
7. **`CONTEXT.md`** в корне проекта — глоссарий. Пиши PRD его терминами.
8. **Репозиторий** — текущее состояние для §2 и пути для §6.1 и §6.5.

### К5. Тех-покрытие и интервью

PRD и `prd-to-beads` нужны тех-факты, которые карта о поведении фичи
часто пропускает. Проверь, что источники К4 покрывают пять пунктов:

| Пункт | Покрыт, когда источники называют | Секция PRD |
|-------|----------------------------------|------------|
| 1. FR с приоритетами | каждое поведение, которое видит пользователь или внешний клиент, и его приоритет `must-have` / `nice-to-have` | §5 |
| 2. Контракт интерфейса | что применимо: эндпоинты (метод, путь, запрос, ответ, ошибки), команды CLI (аргументы, вывод, коды выхода), экраны UI (содержимое, состояния) | §6.2 |
| 3. Модель данных | таблицы или коллекции с полями и типами, индексы, миграции или файлы и их формат; какой компонент читает и пишет какие данные | §6.3 |
| 4. Модули и файлы | путь к коду каждого FR, новый или изменяемый, по слоям | §6.5 |
| 5. Внешние зависимости | сервисы, библиотеки, команды, интеграции; фоновые задачи, очереди, кэш | §6.4, §7 |

Решение «HTTP API» без эндпоинтов или «Postgres» без колонок пункт не
покрывает.

**Сначала репозиторий.** До вопросов найди в репозитории, что можно:
существующие модули, роутеры, модели, миграции, конфиги, зависимости в
манифестах. Для пункта 4 это обязательный первый шаг: пути из скана и
решений карты — основа предложений.

**Раскладка модулей.** Если доступен скилл `codebase-design`, используй его.
Если его нет, сравни границы модулей по ответственности и размеру интерфейса. Строй раскладку его словарём: глубокий модуль за
маленьким интерфейсом, шов, адаптер. Один модуль собирает несвязанные
ответственности (поиск, решение, лимиты и якоря в одном файле) → назови
это и предложи разрезать его по швам. Граница спорная → предложи 2–3
варианта интерфейса на выбор
пользователю. Выбранный вариант запиши как ADR (см. «ADR» ниже).

**Интервью.** Непокрытые пункты закрой коротким интервью с пользователем в
этой же сессии. Подход — факт-фаза `feature-discovery`
(`../feature-discovery/references/facts-interview.md`,
«Правила» и «Раунд 3»), с такими отличиями:

- Вширь: каждый раунд спрашивает по всем ещё открытым пунктам, не
  углубляется в один. Не более 4 вопросов за раунд. Первыми идут пункты
  4 и 1: без них `prd-to-beads` не соберёт задачи.
- Максимум 3 раунда.
- Каждый вопрос несёт готовый ответ из репозитория и решений карты: «Для
  FR-2 предлагаю `backend/app/api/quotes.py::get_quote`, новый. Подтверди
  или поправь». Открытый вопрос — только когда предложить нечего.
- Ответ пользователя — источник наравне с решением карты. В PRD ссылайся
  на него как `(интервью)`.
- Пункт, который пользователь признал неприменимым (нет хранилища, нет
  внешних сервисов), получает в своей секции PRD одну строку: «Не
  применимо: <причина> (интервью)». Пункты 1 и 4 неприменимыми не бывают.
- Что осталось без ответа после 3 раундов, идёт в §11.
- Все пункты покрыты источниками К4 → интервью не нужно, переходи к К6.

**ADR.** Ответ, который выбирает между двумя и более вариантами
(библиотека, хранилище, протокол, контракт API, модель данных), запиши
коротким ADR в `decisions.md` в корне проекта. Формат и нумерация — по
`../senior-developer/references/decisions.md`. Файла нет →
создай его. Альтернативы и причину выбора возьми из интервью. В PRD
ссылайся на `(ADR-NNN)`.

### К6. Маппинг источников → PRD

Каждый факт в §2–§9 заканчивается ссылкой на источник: `(<id>)` для вопроса,
`(<map-id>)` для Destination и Notes, `(ADR-NNN)` для ADR, `(интервью)` для
ответа тех-интервью К5. Решение — один
источник: факт из комментария вопроса и из ADR по этому вопросу ссылается на
оба.

| Секция PRD | Источник |
|------------|----------|
| 1. Обзор | Destination + Концепт «Что это», «Для кого и какой опыт» |
| 1.5 Концепт фичи — Метафора / аналог | Концепт «Что это» — буквальный перенос |
| 1.5 Концепт фичи — Опыт пользователя | Концепт «Для кого и какой опыт» — буквальный перенос |
| 1.5 Концепт фичи — Главный принцип | Концепт «Главный принцип» — буквальный перенос |
| 1.5 Концепт фичи — Чем НЕ является | Концепт «Чем это **не** является» — буквальный перенос |
| 2. Что сейчас происходит | репозиторий + итоги вопросов типа `task` (что сделано, какие факты получены) |
| 2. Почему сейчас | Destination, Notes |
| 2. Материалы | сама карта `карта wayfinder «<название>» (<map-id>)`, `CONTEXT.md`, ADR карты, файлы findings, прототипы |
| 3. В скоупе | Destination + ограничения из Notes + решения о том, что фича делает |
| 3. Не в скоупе | строки Out of scope + исключения, которые решения называют явно («не делаем», «нет», «без») |
| 4. User Stories | роли и сценарий — Концепт «Для кого и какой опыт»; действия — FR из §5 |
| 5. Функциональные требования | ограничения из Notes + решения о поведении, которое видит пользователь или внешний клиент |
| 6.1 Архитектура / компоненты | решения и ADR о стеке, протоколе, компонентах + скан репозитория |
| 6.2 API | решения и ADR с эндпоинтами или контрактом внешнего интерфейса |
| 6.3 Схема БД | решения и ADR со схемой данных |
| 6.4 Прочее | решения и итоги `task` о внешних сервисах, конфигах, фоне, кэше |
| 6.5 Затрагиваемые классы и функции | пути из решений, ADR и findings + FR из §5 + скан репозитория |
| 7. Зависимости | внешние сервисы и команды из решений, Notes и Out of scope |
| 8. Альтернативы | отклонённые варианты из решений, findings и ADR «Alternatives Considered» |
| 9. Риски и ограничения | риски и известные отказы из решений, findings и ADR «Consequences» с (-) |
| 10. Definition of Done | шаблон + критерии приёмки, решённые на карте |
| 11. Открытые вопросы | Not yet specified (у закрытой карты пуст) + пробелы, найденные при сборке |
| 12. История изменений | шаблон: версия 1.0, сегодняшняя дата |

**FR.** Одно FR — одно проверяемое поведение. Приоритет (`must-have`,
`nice-to-have`) пиши, только если его называет карта или интервью К5. Иначе
FR без приоритета.

**Условные секции — включай по таблице:**

| Секция | Включать когда |
|--------|----------------|
| 6.2 API | решения, ADR или интервью К5 задают новый или изменяемый контракт: эндпоинты, команды CLI, экраны UI |
| 6.3 БД | решения, ADR или интервью К5 задают изменения схемы или хранилища |
| 6.4 Прочее | есть внешние сервисы, конфиги, фон, очереди или кэш |
| 7. Зависимости | есть хотя бы одна зависимость |
| 8. Альтернативы | есть хотя бы один отклонённый вариант |
| 9. Риски | есть хотя бы один риск |

Секцию, пункт которой интервью К5 признало неприменимым, включай с одной
строкой «Не применимо: <причина> (интервью)».

**Факт, которого нет на карте.** PRD нужен факт, а его не дают ни
источники К4, ни интервью К5 (контракт API при решённом «HTTP API»,
таблица БД при решённом «pgvector», раскладка модулей) → не выдумывай.
Вопрос в §11, в секции — строка из правила пробелов. Предложение К5 без
подтверждения пользователя фактом не считается.

**Противоречие источников.** Решение вопроса расходится с Концептом или с
другим решением, и более поздний комментарий его не снимает → не выбирай
сам. Вопрос в §11 с обеими цитатами и ссылками.

Дальше — «Общие правила сборки» и «Сохранение и вывод».

## Вход по notes и tech.md

### Н1. Найти notes и tech.md

Пользователь обычно даёт slug или путь.

- Если дан путь к папке фичи или к её `notes.md` → бери его.
- Если дан slug → найди `<root>/<slug>/notes.md`. Корень по умолчанию —
  `docs/features/`. Если проект задаёт свой корень в `CLAUDE.md`, ищи
  папку `<slug>/` рекурсивно (Glob) под этим корнем.

Если notes-файла нет — отказывай в генерации с указанием, что сначала нужен
`/feature-discovery`.

**Запомни папку, где нашёл notes** (`<feature-dir>`). PRD пиши в неё же.
Не определяй проект или сделку заново: иначе notes и PRD разъедутся по
разным проектам.

tech.md ищи только в той же папке: `<feature-dir>/tech.md`. Его
наличие проверяется в шаге Н2, после статуса notes.

### Н2. Валидация discovery

**Н2.1. Статус notes.** Прочитай frontmatter notes-файла.

- `status: discovery-complete` → продолжай
- `status: prd-generated` и `<feature-dir>/prd.md` есть → повторная сборка:
  сохрани прежний PRD в `<feature-dir>/archive/` с версией и датой в имени,
  затем проведи тех-интервью заново. Прежний PRD используй для сравнения,
  а не как источник неподтверждённых решений. При совпадении имени архива
  добавь номер; не перезаписывай сохранённую версию.
- `status: prd-generated`, но PRD нет → откажи: статус и файлы расходятся
- `status: discovery-blocked` → **отказывай в генерации:**
  > Notes помечен как discovery-blocked — концепт не сформулирован.
  > Сначала доработай концепт через /feature-discovery, потом возвращайся.
- Любой другой / отсутствие статуса → отказывай с указанием проблемы

**Н2.2. Концепт в notes.** Разделы с этими заголовками есть и заполнены —
не пустые, не «...», не текст шаблона в `<...>`:

| Заголовок в notes | Элемент концепта |
|-------------------|------------------|
| `## Что это` | метафора / жанр |
| `## Для кого и какой опыт` | опыт пользователя |
| `## Главный принцип` | принцип |
| `## Чем это **не** является` | чем НЕ является |

**Подтверждение концепта** отдельно не проверяется: `feature-discovery`
ставит `status: discovery-complete` только после sanity-check и
reverse-playback с пользователем. Статус из Н2.1 и есть подтверждение.

**Н2.3. tech.md.**

- Файла `<feature-dir>/tech.md` нет → **отказывай в генерации:**
  > Нет tech.md рядом с notes — тех-факты факт-фазы не сохранены.
  > Пройди факт-фазу через /feature-discovery, потом возвращайся.
- `feature` во frontmatter не совпадает с именем `<feature-dir>` → отказывай с указанием
  расхождения.
- Есть все 12 разделов, в каждом (в «Контекст» и «Скоуп» — в каждом поле)
  факты, `нет данных` или `см. notes, «<раздел>»`:
  `## Контекст` (поля «Что сейчас происходит», «Почему сейчас»,
  «Материалы»), `## Скоуп` (поля «В этой итерации», «Не в этой итерации»),
  `## Функциональные требования`, `## Стек и компоненты`, `## API`, `## БД`,
  `## Фон, очереди, кэш, интеграции`, `## Затрагиваемые модули и файлы`,
  `## Зависимости`, `## Альтернативы тех-решений`, `## Риски`,
  `## Открытые тех-вопросы`.
  Раздел или поле отсутствует, пусто или содержит текст шаблона в `<...>` →
  отказывай: это «забыли записать», а не «не обсуждали».
- `## Функциональные требования` = `нет данных` → отказывай: без FR не
  собрать §4 и §5, а факт-фаза требует хотя бы 2–3 FR.
- Ссылка `см. notes, «<раздел>»` ведёт на раздел, которого в notes нет →
  отказывай с указанием ссылки.

Если что-то из этого не прошло — отказывай с конкретным указанием пробела.
Не дополняй отсутствующие продуктовые требования. Пустые технические
разделы допустимы: их закрывают тех-интервью и проектирование шага Н3.

### Н3. Техническое интервью и маппинг → PRD

**Как читать разделы tech.md:**
- факты → источник секции;
- `см. notes, «<раздел>»` → источник — указанный раздел notes;
- `нет данных` → решение на этапе discovery не принималось.

Перед вопросами просканируй проект, проверь ОС, версии инструментов и
зависимости. Из notes и tech.md возьми уже согласованные ограничения;
не спрашивай о них повторно. Подготовь короткую техническую картину:
стек, внешний контракт, хранение данных, внешние зависимости и пути модулей.

Для существенной развилки с несколькими допустимыми вариантами проведи
короткое интервью: не больше 3 раундов и 4 вопросов за раунд. Каждый вопрос
содержит конкретную рекомендацию, 1–2 альтернативы и практическое
последствие выбора. В первом раунде охвати все ещё открытые области,
особенно стек и контракт; затем уточняй только оставшееся. Не проси
пользователя называть файлы, классы или команды, если их можно вывести
из выбранного варианта. Ответы этого интервью — источник PRD с пометкой
`(интервью)`. Если пользователь не выбрал вариант после 3 раундов, сохрани
развилку в §11; не выдавай предложение за принятое решение.

Мелкие обратимые решения принимай сам по ограничениям и состоянию проекта,
помечай их как «проектное решение». Для новой библиотеки проверь актуальную
официальную документацию. Существенный выбор между вариантами запиши в
проектный `decisions.md` по формату
`../senior-developer/references/decisions.md`. Если решение меняет
согласованное поведение, не принимай его за пользователя: вынеси вопрос в §11.

## Общие правила сборки

Используй шаблон из `references/prd-template.md`.

**Всегда включай:** 1, 1.5, 2, 3, 4, 5, 6.1, 6.5, 10, 11, 12.

**Правило пробелов.** Не выдумывай продуктовые факты, которых нет в
источниках входа. Технические пробелы закрывай проектным решением, если
его можно принять по ограничениям и состоянию проекта:
- для всегда включаемой секции (или поля §2 / §3) без данных оставь одну
  строку «Не определено на discovery — см. §11, Q-N» (вход по карте: «Не
  определено на карте — см. §11, Q-N»), а вопрос добавь в §11;
- в §9 вероятность и влияние, которых нет в источниках, пиши «не оценено»;
- в §11 ответственный и дедлайн, которых нет в источниках, пиши «—».

**Секция 1.5 — буквальный перенос.** Текст концепта (разделы notes или
подразделы `## Концепт` карты) переносится целиком, без своих формулировок:
это якорь, подтверждённый пользователем.

**Секция 6.5 (Затрагиваемые классы и функции) — обязательная.**
Распиши все новые и изменяемые классы / функции / модули, разнеся их по слоям
системы (UI / Domain / Data). Каждую помечай `[NEW]` или `[EDIT]` и указывай
путь и описание в одну строку. Эта секция — вход для скилла `prd-to-beads`,
который потом разбивает PRD на вертикальные задачи.

Как собрать §6.5:
1. Возьми известные пути из tech.md, карты, ADR и findings; просканируй
   существующий код и разнеси FR по слоям.
2. Для каждого непокрытого FR сам выбери модуль с ясной ответственностью.
   В новом проекте задай конкретные новые файлы и функции как проектное
   решение; отсутствие соседних файлов не блокирует создание PRD.
3. Проверь метки: `[EDIT]` — файл существует; `[NEW]` — файл ещё не
   существует. Если путь из источника назван `[EDIT]`, но файла нет,
   исправь очевидно устаревший путь по скану или вынеси конфликт в §11.
4. Проверь, что каждая FR имеет место реализации, а §6.5 содержит
   конкретные пути и ответственность. Не подменяй модуль названием папки.
   Если даже после проектирования путь определить невозможно из-за
   неразрешённого продуктового решения, укажи это решение в §11.

**Тест-кейсы и разбиение на задачи в PRD НЕ включай.** PRD описывает *что*
меняется и *почему*; *как тестировать* и *как разбить работу на задачи* —
скоуп скилла `prd-to-beads`, который читает PRD и собирает их в
`<feature-dir>/tasks.md`.

**Дата:** сегодняшняя (есть в системном промпте).

**Файл PRD:** `<feature-dir>/prd.md`, например
`docs/features/export-csv/notes.md` → `docs/features/export-csv/prd.md`.

## Сохранение и вывод

1. Создай или обнови `<feature-dir>/prd.md`. Папки нет → создай её.
   Если принято существенное техническое решение, запиши его в проектный
   `decisions.md` и сошлись на него в PRD.
2. Вход по notes: если статус был `discovery-complete`, смени его на
   `prd-generated`. При повторной сборке сохрани `prd-generated`.
   tech.md меняй только для фиксации нового факта пользователя или
   исправления устаревшего факта; статус пары хранится в notes.
3. Вход по карте: notes.md и tech.md не создавай, карту не меняй. ADR
   интервью К5 уже записаны в `decisions.md`.
4. Запиши запись фичи в блок SPEC проектного `CLAUDE.md` (оба входа, см.
   «Блок SPEC в CLAUDE.md» ниже).
5. Выведи в чат:

```
PRD сохранён: <feature-dir>/prd.md
CLAUDE.md: запись <slug> в блоке SPEC обновлена

Концепт фичи в секции 1.5 — это якорь. Если в реализации возникнет
спорный FR/UI-конфликт, сверяйся с этим разделом.

Внеси правки если нужно.
```

Вход по карте: перед последней строкой добавь число вопросов §11 и их
темы одной строкой, номера новых ADR, а при папке без строки `Папка:` —
выбранный slug.

## Блок SPEC в CLAUDE.md

Проектный `CLAUDE.md` загружается в каждую сессию. PRD сам не загружается:
сессия правок по замечаниям о нём не знает и делает то, что PRD исключил.
Блок SPEC даёт каждой сессии ссылки на документы фичи и её «Не делаем».

**Где.** `CLAUDE.md` в корне проекта (корень git-репозитория). Файла нет →
создай его только с блоком.

**Шаблон блока.** Одна запись `### <slug>` на фичу:

```markdown
<!-- BEGIN SPEC -->
## Спецификации фич

Перед работой по фиче прочитай её PRD. Пункт из «Не делаем» не реализуй:
задача требует его → остановись и спроси. Правка меняет поведение или
скоуп → обнови PRD, ADR и этот блок в том же коммите.

### <slug>
- PRD: `<feature-dir>/prd.md`
- ADR: `decisions.md`
- Глоссарий: `CONTEXT.md`
- Не делаем (источник: PRD §3; при изменении правь PRD и этот блок):
  - <пункт «Не в скоупе»>
  - <пункт «Не в скоупе»>
<!-- END SPEC -->
```

**Как заполнить запись:**

- Строку ADR пиши, если `decisions.md` есть в корне проекта. Строку
  глоссария пиши, если есть `CONTEXT.md`.
- «Не делаем» — каждый пункт «Не в скоупе» из §3 нового PRD отдельной
  строкой. Оставь суть пункта, обоснование отрежь. Одна строка — до
  ~100 символов.
- §3 «Не в скоупе» без пунктов («Не определено…») → одна строка
  `  - не определено, см. PRD §11`.

**Как записать:**

1. Маркеров `<!-- BEGIN SPEC -->` и `<!-- END SPEC -->` нет → добавь блок в
   конец файла. Блок не ставь внутрь чужого управляемого блока: между
   другими парами BEGIN/END (например, блок beads) не пиши.
2. Маркеры есть → меняй текст только между ними. Запись `### <slug>` есть →
   замени её от заголовка до следующего `### ` или до `<!-- END SPEC -->`.
   Записи нет → добавь её перед `<!-- END SPEC -->`.
3. Записи других фич и текст вне маркеров не трогай.

## Тон и стиль

- Документ на русском, код / SQL / JSON — на английском
- **Вход по notes: проведи короткое техническое интервью.** Объясняй
  варианты и последствия; не спрашивай заново уже согласованные факты.
  Отказывай только при неготовом или невалидном discovery
- **Вход по карте: вопросы — только тех-интервью К5**, до 3 раундов. Что
  осталось без ответа, идёт в §11. Отказ — только по проверкам К2, К3 и
  по пустой §6.5
- **НЕ додумывай пользовательское поведение.** Инженерные решения
  формулируй явно, обосновывай и записывай в ADR при существенном выборе
- Концепт-секция (1.5) — самая важная. Переноси её буквально, без
  своих формулировок. Якорь должен оставаться тем же, что подтвердил
  пользователь
