# Как собрать и пополнять набор проверок агента

Проверочная задача описывает поручение агенту, исходное состояние и признак успеха. Один запуск агента на этой задаче — одна попытка. Если агент пишет программу, её тест может служить проверкой результата этой попытки.

## С чего начать

1. **Выберите одну задачу.** Например, агент должен написать программу, которая выводит номера медленных запросов из журнала сервера.
2. **Запишите критерий успеха.** В отчёт входят все запросы длительностью 500 мс и более, каждый ровно один раз. Порядок номеров произвольный.
3. **Подготовьте вход и ожидаемый результат.** Запрос A длился 499 мс, B — 500 мс, C — 501 мс. В отчёте должны быть только B и C. Сохраните исходный журнал и ожидаемый ответ до запуска агента.
4. **Выберите способ проверки.** Здесь скрипт может запустить программу и сравнить весь список с ожидаемым, учитывая число повторов каждого номера. Если результат оценивает человек, запишите правило, по которому он примет или отклонит работу.
5. **Проверьте саму проверку.** Отчёт с одним C должен дать ошибку «пропущен B», отчёт с B, B и C — ошибку «B повторяется». Списки B, C и C, B должны пройти.
6. **Выполните базовый прогон.** Дайте агенту поручение в чистой рабочей копии. Сохраните версии модели, инструкций и инструментов, полученный результат и вердикт проверки. Для разбора ошибок пригодится трейс — запись вызовов инструментов и ответов среды.
7. **Сравните версии.** После изменения агента повторите те же задачи из того же исходного состояния. Если результат меняется от запуска к запуску, выполните несколько попыток для каждой версии и сравните число успешных.
8. **Пополняйте набор.** Для нового случая запишите, какую ошибку он обнаружит. Если изменилось требование, обновите критерий и ожидаемый результат вместе и укажите, с какой версии они действуют.

## Пример проверки отчёта

Инженер попросил агента написать программу для отбора медленных запросов. Для проверки он сохранил журнал из трёх строк.

| Номер запроса | Длительность | Ожидаем в отчёте |
|---|---:|---|
| A | 499 мс | Нет |
| B | 500 мс | Да |
| C | 501 мс | Да |

В первом прогоне программа вывела только C. По журналу видно, что пропущен B с длительностью ровно 500 мс. Инженер открыл код и нашёл условие `duration_ms > 500`.

После замены условия на `duration_ms >= 500` инженер повторил тест с тем же журналом. Программа вывела B и C по одному разу. На этих данных отчёт совпал с ожидаемым. Инженер сохранил тест, чтобы повторять его после следующих изменений.

## Откуда брать новые случаи

| Источник | Что включить в набор |
|---|---|
| Типовые рабочие задачи | Возьмите частые поручения из очереди задач. Сохраните формулировку, вход и признак успеха. Так набор будет отражать повседневную работу. |
| Реальные сбои | Возьмите неудачный запуск и выделите условия, при которых видна ошибка. Например, команда завершилась до запуска тестов, а агент сообщил, что все тесты прошли. |
| Ручные исправления и повторные обращения | Посмотрите, что человек переделал после сдачи работы. Если инженер вручную удалил дубликаты из отчёта, добавьте проверку числа вхождений каждого номера. |
| Требования и договорённости | Превратите уточнение заказчика в проверку. Договорились включать запрос ровно на пороге — добавьте строку с длительностью 500 мс. |
| Граничные случаи | Найдите минимальное изменение входа, при котором должен измениться ответ. Для порога проверьте значения ниже, ровно на границе и выше. Для списка — пустой список и один элемент. |
| Редкие ошибки с серьёзными последствиями | Возьмите действие, после которого трудно восстановить данные. Если пользователь просит создать копию файла, проверьте и содержимое копии, и сохранность оригинала. |
| Неясные поручения и недостающие данные | Составьте пару задач. В первой порог задан — агент может продолжить. Во второй порог пропущен, значения по умолчанию нет — агент должен задать вопрос. |
| Сбои среды и прерывания | Включите потерю доступа, тайм-аут или исчерпание лимита. Если инструмент создал запись, но ответ потерялся, проверьте, что после возобновления в системе ровно одна запись. |
| Варианты знакомой задачи | Измените деталь, которая по требованию не влияет на результат. Переставьте строки журнала и проверьте, что состав отчёта сохранился. |
| Обновления и миграции | Если программа должна читать старый формат, сохраните пример файла предыдущей версии. После обновления проверьте, что программа читает его и выдаёт ожидаемый результат. |

## Какие примеры оставить для независимой проверки

Заранее отложите часть задач. Зафиксируйте инструкции агента и правила оценки, затем запустите отложенные задачи. Так вы увидите, как конфигурация работает на примерах, которых при настройке не видели.

Если по ошибке в отложенной задаче вы уже изменили инструкции или правило оценки, сохраните её для проверки регрессий. Для следующей независимой оценки возьмите свежие задачи.

## Шаблон проверки своей задачи

Скопируйте вопросы в рабочий файл. Заполните первые четыре поля до запуска, последние два после него.

```text
Поручение. Что должен сделать агент?
Исходные данные. С какими данными и в каком состоянии он начинает работу?
Критерий успеха. Какое наблюдаемое свойство вы проверите?
Ожидаемый результат. Что именно должно получиться на этих данных?
Фактический результат. Что вы увидели и где это зафиксировано?
Вывод. Выполнен ли критерий? Какое наблюдение это подтверждает?
```
