# Вторая лекция: контекст, память и задачи

Текст к встрече 10 ноября 2026 года. Версия от 11 ноября. Источник для самостоятельного чтения и навыка study.
Учебные примеры показывают приёмы работы. Они не описывают проекты участников.

## 1. Контекст

### Что модель получает сейчас

Контекст — сведения, которые модель получает при одном обращении: инструкции, история разговора и результаты инструментов.
Контекстное окно — предел этого объёма в токенах. Размер окна зависит от модели и доступного режима работы.

Агент действует в несколько шагов. Он читает файл, получает результат, выбирает следующее действие.
Клиент собирает контекст для каждого обращения к модели. Поэтому доступная папка и текущий контекст — разные вещи.

Например, в папке лежат десять инструкций. Агент прочитал две. Наличие остальных восьми на диске не означает, что модель учитывает их содержание.
Попросите назвать использованные источники и проверьте чтение нужного файла в ленте действий.

Файл можно поручить найти агенту или указать самостоятельно. В Claude Code `@путь-к-файлу` помогает добавить известный материал.
Указание папки не означает чтение всех вложенных файлов. Большой документ лучше читать по разделам, сохраняя условия и определения.

При старте часть контекста уже занята инструкциями клиента, описаниями инструментов и загруженными правилами.
Поэтому новая сессия не означает полностью пустое окно. Команда `/context` помогает увидеть его состав и заполнение.

### Что происходит в длинной сессии

История накапливает сообщения, прочитанные материалы, ошибки и результаты проверок.
Полезные сведения могут смешиваться с устаревшими решениями и выводом, который больше не нужен.
Большое окно позволяет передать больше текста, но не гарантирует одинакового качества на любом объёме.

HumanLayer описывает практический ориентир: поддерживать заполнение окна в пределах 40–60% при работе с кодом.
Это опыт команды с учётом сложности задачи. Универсальный порог ухудшения для всех моделей из него не следует.
При окне 200 тысяч токенов такой диапазон составляет 80–120 тысяч. Это пример пересчёта, а не отдельное измерение качества.
В объём входят все части контекста, а не только ваши сообщения. [Источник ориентира](https://www.humanlayer.dev/blog/advanced-context-engineering).

Если агент пропустил требование, сначала проверьте, прочитан ли источник и нет ли противоречий.
Сам по себе процент заполнения не доказывает причину ошибки. Сравнивайте результат с условиями задачи.

### Очистка, сжатие и новая сессия

Сжатие заменяет историю сводкой. В Claude Code его можно вызвать через `/compact`.
Сводка может потерять подробности, поэтому важные решения и незавершённые шаги стоит сохранять в проверяемом файле.
После сжатия сверьте сохранённые ограничения и следующий шаг.

Очистка через `/clear` начинает разговор без прежней истории. Файлы проекта при этом не удаляются.
Правила, которые клиент загружает при старте, продолжают действовать. Но произвольный файл плана нужно явно прочитать.

Новая сессия подходит для другой задачи или продолжения по сохранённому состоянию.
Возврат через `/resume` позволяет продолжить существующий разговор. Это другой способ работы, чем восстановление по файлам.

Пример: вы закончили анализ документа и переходите к другой задаче. Сохраните нужный вывод и начните новую сессию.
Если задача продолжается, сохраните ограничения, принятые решения, проверки и следующий шаг, затем восстановите их из файла.

### Остановка и откат

Остановка прерывает текущую работу агента, но не отменяет уже выполненные действия.
В терминале Claude Code `Esc Esc` при пустом поле ввода открывает меню отката.
Можно выбрать возврат разговора, поддерживаемых правок файлов или обоих состояний.

Откат клиента охватывает не все изменения. Действия через оболочку, внешние приложения и сервисы требуют отдельной проверки.
После отката посмотрите фактические файлы. Контрольные точки агента не заменяют историю Git и резервные копии.

Побочный вопрос, ответ на который уже есть в разговоре, можно задать через `/btw`.
Ветвление разговора позволяет попробовать другую мысль. Оно само по себе не создаёт отдельную копию рабочих файлов.
Способы вызова и ограничения перечислены в [памятке](cheatsheet.md).

## 2. Память

### Как сведения переживают сессию

Память агента — сохранённые сведения, которые можно загрузить в следующий контекст.
В рассматриваемом процессе это файлы правил, заметки и документы проекта. Запись в них не меняет веса модели.

Чтобы сохранённое повлияло на ответ, клиент или агент должен прочитать его.
Поэтому просьба «запомни» требует проверки: что записано, куда и как будет загружаться.
Если агент только ответил «запомнил», сохранение ещё не подтверждено.

Правило выбирают по области действия. Общее соглашение нужно команде, личная привычка — конкретному человеку.
План одной задачи и её текущие ошибки обычно не нужны в инструкциях всех будущих сессий.

### Где хранить

| Сведения | Подходящее место |
|---|---|
| Личные предпочтения во всех проектах Claude Code | `~/.claude/CLAUDE.md` |
| Общие правила конкретного проекта | `CLAUDE.md` проекта |
| Личные правила только этого проекта | `CLAUDE.local.md` |
| Правила по темам или группам файлов | `.claude/rules/` |
| Заметки автоматической памяти | Каталог памяти проекта внутри `~/.claude/projects/` |
| Причины принятых решений | Принятый в проекте журнал решений |
| Шаги и состояние одной задачи | Файл плана или существующий трекер |

Это расположение относится к Claude Code. В другом клиенте сначала проверьте механизм загрузки инструкций.
В учебном репозитории общие правила находятся в `AGENTS.md`, а `CLAUDE.md` подключает их.
Сохраняйте существующее устройство проекта: второй конкурирующий набор правил затрудняет проверку.

На Windows домашнюю папку откройте через `%USERPROFILE%` в Проводнике. На macOS и Linux ей соответствует `~`.
Личные файлы не следует добавлять в общий Git. В учебном комплекте `CLAUDE.local.md` исключён через `.gitignore`.
Исключение не удаляет ранее опубликованный файл из истории.

### Автоматическая память

Claude Code может самостоятельно сохранять полезные наблюдения в файлы памяти проекта.
Индекс `MEMORY.md` загружается частично: первые 200 строк или 25 КБ, в зависимости от того, какой предел достигнут раньше.
Подробные заметки читаются по необходимости. Каталог по умолчанию находится вне репозитория, поэтому коллега не получит его обычным клонированием.

Команда `/memory` помогает проверить память и инструкции. Доступность зависит от среды и версии.
Полезно спросить: «Какие сведения ты используешь? Назови файл для каждого пункта».
Затем откройте один указанный файл и сверьте утверждение. Ответ агента о собственных источниках тоже может быть ошибочным.

Запись памяти может устареть. Подтверждённое командное решение закрепляйте в общем документе проекта.
Локальная заметка агента не должна быть единственным местом хранения такого решения. [Документация памяти](https://code.claude.com/docs/en/memory).

### Правила и решения

Правило говорит, как действовать. Решение объясняет сделанный выбор и его причину.
Например, «результаты упражнения храним в work/» — правило.
«Выбрали work/, чтобы повторные попытки не меняли материалы курса» — запись о решении.

Для небольшой задачи достаточно журнала с датой, контекстом, решением, причиной и отклонёнными вариантами.
При изменении решения укажите, какую прежнюю запись оно заменяет. Не удаляйте причину прежнего выбора без необходимости.

Инструкцию можно проверить по наблюдаемому поведению. Вместо «работай аккуратно» напишите: «Перед изменением назови целевой файл».
Не превращайте каждую случайную неудачу в постоянный запрет. Сначала определите причину и область действия правила.
Периодически удаляйте устаревшее и устраняйте противоречия.

Текстовая инструкция влияет на действия модели, но не обеспечивает техническую блокировку.
Обязательное ограничение требует подходящего механизма разрешений или проверки инструмента.
Повторяемую процедуру можно оформить навыком, как уже сделано для study.
Образцы — в [отдельном материале](examples.md).

## 3. Задачи и план

### Задача и сессия

Задача описывает результат и критерии его готовности. Сессия — отдельный разговор с агентом.
Одна задача может занимать несколько сессий. Её состояние должно оставаться доступным после завершения разговора.

Для короткого действия подробный план может быть лишним. Он полезен, когда есть несколько шагов, неизвестные условия или существенные последствия.
До выполнения задайте цель, источники, ограничения, ожидаемый результат и проверку.

Пример цели: подготовить краткую памятку по четырём темам лекции.
Критерий готовности: каждая тема содержит действие и способ проверить его, а все локальные ссылки открываются.
Фраза «памятка хорошая» не определяет проверку.

### Режим планирования

В режиме планирования агент изучает материалы и предлагает порядок действий перед изменением рабочих файлов.
Клиент может сохранять собственный файл плана. Это не означает, что уже создан документ плана в выбранной папке проекта.

Прочитайте план до одобрения. Проверьте границы правок, недостающие решения и критерии готовности.
Исправьте неверное понимание источников или результата. После одобрения поручите сохранить согласованный план в проекте первым шагом.

Режимы и способы переключения различаются между терминалом и Desktop. Пользуйтесь [памяткой](cheatsheet.md), соответствующей вашей среде.
Если режима нет, попросите сначала предложить план без изменения рабочих файлов и проверьте соблюдение этого ограничения.

### Что сохранять в плане

В плане нужны цель, границы, источники, критерии готовности, шаги, открытые вопросы и текущее состояние.
Состояние может содержать выполненное, результаты проверок и следующий шаг. Для небольшой задачи отдельный файл состояния не обязателен.

Отмечайте шаг выполненным после проверки его результата. Если проверка не запускалась, так и запишите.
Изменение требований должно отражаться в плане: иначе следующая сессия продолжит по устаревшей задаче.

Запрос продолжения должен назвать файл. Например:

```text
Прочитай план задачи. Сверь отмеченное выполнение с фактическими файлами.
Назови оставшееся и предложи следующий шаг. Пока ничего не меняй.
```

Если в плане написано «файл готов», а файла нет, состояние противоречиво.
Нужно выяснить причину, а не повторять отметку из плана как подтверждённый факт.

### Когда нужен трекер

Список шагов в разговоре удобен во время одной попытки. Файл плана удобен для передачи задачи между сессиями.
Трекер помогает, когда задач много, есть зависимости, ответственные и параллельная работа.

Beads и GitHub Issues — примеры трекеров. Выбирайте принятый в команде способ хранения задач.
Подключение агента требует доступного инструмента и нужных полномочий. Установка нового трекера не является условием этой практики.

Статус задачи и фактическая проверка результата — разные сведения. Закрытая карточка сама по себе не доказывает, что результат работает.
Команда `/tasks` в Claude Code показывает фоновую работу; она не заменяет список задач проекта.

## 4. Состояние

### Что проверять после перерыва

Состояние проекта — проверенная сводка: что сделано, что работает, что осталось и какие действия ещё выполняются.
Её собирают из файлов, результатов проверок, трекера и доступных сведений о процессах.

Для документа достаточно проверить готовые разделы, источники, ссылки и открытые вопросы.
Для приложения могут понадобиться сборка и тесты. Для исправления ошибки — воспроизведение ошибки и проверка исправления.
Состав сводки определяется критериями задачи.

В папке из ZIP может не быть Git. Тогда нельзя достоверно назвать ветку или историю коммитов.
Можно проверить текущие файлы и сопоставить их с планом. Отсутствие Git не мешает этой проверке.

Если в проекте не настроены тесты, нельзя сообщать «тесты прошли».
Если фоновый процесс недоступен текущему клиенту, его состояние остаётся непроверенным.
Отсутствие доступа и отсутствие процесса — разные выводы.

### Как запросить доказательства

Полезный запрос связывает каждый вывод с основанием:

```text
Проверь состояние задачи по плану и фактическим файлам.
Для каждого критерия укажи результат, способ проверки и основание.
Раздели выполненное, невыполненное и непроверенное. Назови следующий шаг.
Рабочие файлы не меняй. Проверки с побочными эффектами сначала перечисли.
```

Основанием может быть команда и её вывод, конкретный фрагмент файла или результат ручной сверки.
Просмотрите хотя бы одну проверку самостоятельно. Агент может выполнить неподходящую команду или неверно истолковать её результат.

Например, существование `summary.md` доказывает наличие файла. Оно ещё не доказывает наличие всех четырёх тем.
Проверка числа заголовков также не доказывает правильность содержания. Проверяйте тот признак, который задан критерием готовности.

### Как закончить работу

Перед завершением обновите план: результат, проверенное, ограничения, открытые вопросы и следующий шаг, если он нужен.
В новой сессии назовите этот файл и попросите сверить его с текущим состоянием.
Так передача работы опирается на доступные источники, а не на обещание агента помнить разговор.

Для переноса приёма на свою задачу выполните [задание к трекингу](homework.md).
